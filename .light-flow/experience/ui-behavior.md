# Опыт: поведение UI

Уроки спринта 02 (бильярд), фаза 04-c. Каждый урок оплачен найденным дефектом.

1. **Новый вариант элемента → аудит глобальных селекторов.** `input` в
   `src/styles/base.css:55-61,83-93` накрыл `input[type="range"]`: слайдер силы
   получил `cursor: text`, `user-select: text`, фон/рамку/паддинги текстового
   поля. Исключения были только для checkbox/radio. Правило: добавляя вариант
   элемента, grep'ать глобальные селекторы, под которые он попадает.
   **Спринт 03 (02-c): вылечено в источнике** — range исключён из общих правил
   (`input:not([type="range"])`) и получил свой вид (`appearance:none` + трек и
   бегунок); точечных исключений на месте не плодим.
2. **Меняющиеся числа → `tabular-nums` + место под максимум.** Подпись «N%»
   (`BilliardsUi.vue:279-282`, `min-width: 3.5ch` без tabular-nums) прыгала
   30.19 → 38.97px, панель росла 412.98 → 421.61px на «100%». Крайние значения
   (0/100) проверяются первыми — это первое, что смотрят у контролла.
3. **Нативный `range` в боксе текстового поля ломает геометрию.** `appearance:
   auto` + `box-sizing: border-box` + `padding: 8px 12px` + `border: 1px` при
   width 220 дали content-box 194px: бегунок физически не доходит до края.
   Стилизация range — решённая задача (`appearance: none` + свой thumb), не
   изобретать.
4. **Отладке не место в прод-UI.** `revision {{ snapshot.revision }}`
   (`SessionHost.vue:48`) виден игроку. Отладочное — в тестовую игру/HUD, не в
   игровой слой.
5. **Две точки перевода координат без общего хелпера расходятся молча.**
   `angleFromEvent` считает fit от `getBoundingClientRect`
   (`BilliardsUi.vue:62`), рендер — от `frame.size` (`render.ts:118`). Пока
   совпадают; при CSS-повороте (D4) разойдутся. Общий хелпер до фазы ориентации.
6. **Состояние только-для-вида — в рантайм-слот, влияющее на ход — в `Move`.**
   Прицел и поставленный биток живут несериализуемыми рантайм-слотами (как
   `#aim`), чтобы не пачкать `BilliardsState`/сохранения; но позиция битка
   влияет на результат — поэтому она входит в ход (`{angle, power, cueY}`),
   иначе сериализация/сеть не воспроизведут удар (спринт 03, 02-b).
 7. **Все ветки рендера получают один и тот же набор параметров вида.**
   Ранний `return` в `BilliardsGame.draw` для реплея передавал опции без
   `bottomInset` — на время анимации стол вписывался крупнее, и панель его
    перекрывала; после покоя скачок возвращался (спринт 03, 02-c). Наблюдаемый
    «дёргается только во время удара» — почти всегда разница параметров между
    ветками рендера.
 8. **При частом изменении входов дорогой preview должен менять поколение, а не
    перезапускать полный точный расчёт на каждом событии.** Удерживать последний
    полный результат, после короткой тишины считать новое поколение малыми
    порциями фиксированного physics `dt` и постепенно наращивать бюджет; старые
    поколения отменять, а результаты переключать атомарно. Кэшировать неподвижные
    слои только с ключом по всем отображаемым входам. Контакт физики регистрировать
    в collision resolver, не искать только по уже скорректированной позиции после
    шага. Применено в бильярде: `preview.ts:66`, `physics.ts:333`,
     `render.ts:250,334` (01-c, 2026-10-11).
  9. **Непрерывный контрол должен отзываться во время ввода, не блокировать
     debounce-паузой.** Коалесцировать частые изменения до одного обновления за
     кадр, сразу показывать дешёвый актуальный результат и уточнять после
     остановки. Иначе линия прицела выглядит сломанной, хотя новый расчёт ждёт
     тишины. Исправлено в бильярде 01-c: `preview.ts` считает live-оценку за кадр
     (первый кадр 128 точных шагов, рост до 240) без паузы; `game.ts` кэширует
     поставленное состояние по идентичности (`#placedCueCache`), иначе
     `withPlacedCue` каждый кадр давал новый объект и сбрасывал preview.
     Подтверждено вживую: протаскивание угла обновляет линию каждый кадр, после
     установки битка прицел возобновляется. Стоимость кадра на полной пирамиде —
     ~3–4 мс в среднем, ~8 мс худший (замер).
10. **У каждого пути ввода одного контролла должны быть одинаковые побочные
    действия, иначе часть пути «молчит».** Пошаговое уточнение preview запускалось
    из перетаскивания по столу и из силы, но не из тонкой шкалы угла: после
    подстройки шкалой путь оставался частичным (`BilliardsUi.vue:156-167`,
    исправлено в 01-c). Правило: добавив новый способ менять параметр, сверь, что
    он зовёт те же `requestDraw`/`pumpPreview`/`sync`, что и существующие.
11. **Лаг, который виден только при открытых DevTools, — не баг приложения.**
    Лаг перетаскивания биток (спринт 04, 02-b) не воспроизводился при закрытых
    DevTools и при включённой записи Performance. Журнал с открытыми DevTools
    показывал разрывы кадров 30–75 мс при 12 fps, а замер `draw()` — 0.5 мс: время
    уходило вне кода приложения. Гипотезы по коду (пересборка слоя шаров,
    перевыделение холста, реактивность Vue) были ложными или неважными. Правило:
    перед оптимизацией воспроизвести лаг в обычном режиме работы (без DevTools);
    замер журналом вести только в таком же режиме, иначе картина искажена.
    Оптимизации, которые не меняют поведение и упрощают код (не перевыделять холст,
    не обновлять `size` без изменения), оставляем; журнал выключаем (`enabled = false`).
12. **Ход агента обязан идти тем же путём, что ход человека, иначе фаза залипает.**
    Платформа применяет удар компьютера мгновенно (`Session` зовёт `chooseMove` →
    `makeMove`), минуя реплей. В бильярде это давало «телепорт» поля и оставляло
    фазу `passing`: `acknowledgeTurn` звал только человеческий поток, `shoot()`
    блокировался — игра вставала. Решение 02-c: `chooseMove` возвращает `null`, а
    ход ИИ ведёт UI игры тем же циклом, что человека (`startShot` → реплей →
    `makeMove` → плашка → `acknowledgeTurn`). Правило: если у игры есть свой цикл
    хода (реплей/анимация), автозапуск агента платформой надо глушить, а не
    достраивать параллельный путь.
13. **Сетевой слой передаёт непрозрачный ход игры; применяет его тот же путь,
    что локальный.** Платформенный протокол был зашит на `{t:"move",x,y}` — состав
    удара разбирало ядро сети. Обобщение (02-d): сообщение несёт `m: Move`, а
    платформа его не разбирает. И главное: входящий ход нельзя применять прямым
    `session.makeMove` — иначе у игры с реплеем поле телепортируется и цикл хода
    обходится (та же болезнь, что у хода компьютера, п.12). `NetLink` получил хук
    входящего хода, и игра сама решает: проиграть реплеем → применить → плашка →
    `acknowledgeTurn`. Фолбэк на `makeMove` остаётся для игр без реплея.
14. **Живое состояние для соперника — коалессер «последнее значение», а сигнал
    старта — после успешного старта, не до.** Трансляция прицела/силы/битка идёт
    не чаще ~30/с: первое значение сразу, хвост по таймеру, старое отбрасывается
    (иначе поток `pointermove` забивает канал). Сигнал «удар начался» слать
    **после** успешного `startShot`, а не до: реплей шагает по кадрам, поэтому
    «до реплея» сохраняется, но при отказе старта партнёр не ждёт напрасно
    (02-e, `BilliardsUi.vue` `beginShot`, `prep-stream.ts`).
15. **Сеттер с гейтом локального ввода нельзя переиспользовать для сетевых
    данных.** Мост писал позицию битка соперника через `setCuePlacement`, а тот
    закрыт проверкой `canPlaceCue()`: при чужом ходе запись молча отбрасывалась —
    биток не двигался, а линия прицела рисовалась из старой точки. Правило: данные
    из сети идут отдельным методом без локальной валидации (она уже сделана на
    стороне источника); общий гейт оставлять только локальному вводу. 02-e,
    `game.ts` (`setParticipantCue` рядом с `setCuePlacement`).
16. **Изменение вида вне сессии требует явного запроса перерисовки.** Основной холст
    рисуется по требованию (не каждый кадр), поэтому данные, пришедшие по сети
    (кадр подготовки, смена чужого прицела/битка), не появлялись, пока что-то
    постороннее не попросит кадр (ресайз окна). Правило: после записи состояния из
    сети звать `requestDraw` игры. 02-e, `net.ts` (`deps.requestDraw`).
