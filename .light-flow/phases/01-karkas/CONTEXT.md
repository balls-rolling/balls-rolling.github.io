# CONTEXT — Фаза 01: Каркас

## Что делает фаза

Git-репозиторий уже инициализирован (`main`, коммитов нет). Фаза создаёт рабочий
каркас проекта: сборка vite + vue + ts, prettier, базовая тема с токенами.
**Готово** — значит: `npm install` проходит, `vue-tsc` без ошибок, `vite build`
собирается, в браузере видно работающее приложение со светлой/тёмной темой из ОС
и подхваченным системным акцентом. Портируется `theme/palette.js` из исходника.

## Принятые решения

### D1. Структура каталогов — по слоям

```
src/
  core/     — ядро: Game (платформа-синглтон), базовые классы, интерфейсы,
              Session, Player, хранилище, палитра
  ui/       — универсальный инструментарий платформы: сервисы (диалоги, окна,
              всплывающие панели) и компоненты (кнопки, иконки, формы, списки)
  games/    — игры: tic-tac-toe/, <будущие игры>
  styles/   — токены темы, базовые стили
```

Игра лежит в папке со **свободным именем**; её название хранится **внутри** игры
как `id` и `label`. Нумерации вида `game1`/`game2` не будет — id от папки не
зависит, переименование папки не ломает импорты.

### D2. Ядро, UI и игры разделены по ответственности

- **Ядро** — чистые классы, функции и интерфейсы. Поведение и данные.
- **`ui/`** — универсальный инструментарий, ничего не знающий о назначении.
  Компоненты не знают, для чего их используют: кнопка просто кнопка, форма просто
  форма. Связи устанавливает `Game`, вызывая их по назначению.
- **Специфика рождается в момент использования.** Платформа использует UI-инструменты
  по-своему, игры — по-своему. Переиспользуемые фичи отделяются от
  специфичных для игры; игра может добавить свои, но через тот же интерфейс.
- **Игровое окружение** — то, что передаётся сессии при создании. Игры работают
  только с интерфейсами окружения, как в песочнице, отделённой от платформы.
  Собственные инструменты игры добавляются в окружение **плагинами** игры.
- **`Game` не знает ни одной конкретной игры.** Он знает, *как узнать*, какие
  игры доступны. Работает только с записями игр.

### D3. Окружение собирается целиком, песочница отменена

Ранее предполагались заглушки (Null Object) и capability-граница. **Отменено.**
Разработка ведётся в одном проекте, поэтому окружение собирается полностью и
игра получает всё, что запросила. Платформа собирает окружение из заявки игры:
сервисы `ui/` плюс плагины самой игры.

Граница демо обеспечивается **не тем, что игра может**, а тем, **какие слои
смонтированы**.

### D4. Три визуальных слоя, одна страница

Всё происходит на одной странице, без перезагрузок и переходов.

| Слой | Содержимое |
| --- | --- |
| 1. Игровое поле | Холст (canvas) |
| 2. Слой игрового UI | Элементы игры плюс **общие функции поверх**: меню, во весь экран и т. п. |
| 3. Диалоги и окна | Самый верхний слой |

**Следствие для демо: слои 2 и 3 в демо-сессии не монтируются.** На экране
остаётся только слой 1 вместе со всем, что игра рисует сама внутри поля, включая
собственный UI игры внутри поля. Это проще заглушек: нечего поддерживать и нечего
обходить.

### D5. Список игр — на этапе сборки

`Game` получает список игр из папки `games`. Ожидается, что при сборке
генерируется JS со списком записей. Кандидат на реализацию — `import.meta.glob`
в Vite; **требует проверки в execute**, здесь как решённое не зафиксировано.
Формат записи игры: id, лейбл, точка входа, плагины окружения, точка демо.
У плагинов есть **точка входа**, из которой платформа забирает их перед запуском.

### D6. Отложено сознательно

- `pinia` — **не подключаем.** Состояние платформы — composables поверх
  реактивности Vue. (Из `BACKLOG.md`.)
- ESLint — **позже**, когда появится что проверять. Сейчас только prettier, чтобы
  не получить конфликт форматирования при последующем подключении.
- vitest — в фазе 06 вместе с логикой игры.
- Имя каталога `balls-rolling` — **оставляем**, как и название проекта.
  (Из `BACKLOG.md`.)

## Отклонённые варианты

| Вариант | Почему отклонён |
| --- | --- |
| `games/game1`, `games/game2` | Имена теряют смысл при росте числа игр; id не зависит от папки (D1) |
| Заглушки Null Object для демо | Игра в том же проекте, изоляция не нужна; обход заглушек всё равно потребовал бы контроля. Демо решается слоями (D3, D4) |
| Capability-песочница: игра не может дотянуться до платформенного UI | Та же причина — изоляция отнимает больше, чем даёт (D3) |
| Статический список игр импортами | Затрудняет отложенную загрузку и подключение заранее собранных игр |
| Подключение заранее собранных игр по URL | Возможно, но цена: общая часть должна стать пакетом с версией, игра не должна импортировать внутренности платформы, нужна совместимость версий. Сейчас не в объёме; **контракт единой точки входа фиксирует совместимость на будущее** (D5) |
| `pinia` для состояния платформы | Лишняя абстракция поверх composables; в проекте с принципом минимализма лишних зависимостей быть не должно (D6) |
| ESLint на старте | Пока нечего проверять; prettier настроен так, чтобы ESLint не конфликтовал с ним потом (D6) |

## Что делаем на этой фазе

1. Инициализация проекта vite + vue + ts, запуск и проверка сборки.
2. Prettier с конфигурацией, совместимой с будущим ESLint.
3. `styles/`: токены темы. Переносятся дизайн-токены исходника (`--bg-1`,
   `--bg-2`, `--bg-3`, `--bg-m1`, `--card`, `--fg`, `--line`, `--accent`,
   `--accent-2`, `--ok`, `--danger`, `--shadow`, `--radius`, `--radius-sm`) и
   приём с `color-mix(in oklch, ...)` под фиксированный тёмный текст ради
   контраста в обеих темах.
4. Палитра: `prefers-color-scheme` + проба системного `AccentColor` через скрытый
   элемент + фолбэк `#3da96a`, реакция на смену системной темы.
5. Три слоя как заготовка каркаса — на этой фазе без наполнения, чтобы границы
   зафиксировались в коде до начала фазы 02.
6. Критерий готовности: `vue-tsc` чист, `vite build` собирается, тема
   переключается вместе с ОС, акцент подхватывается.

## Открытые вопросы

- Точная структура `Game` как синглтона и как он поднимает UI-контролы (главное
  меню, диалоги) — это основное содержание фазы 02. На фазе 01 нужна только
  заготовка слоёв.
- Формат записи игры и механизм получения списка из `games/` — проверить в
  execute; на эту фазу влияет только базовая согласованность импортов.
- Node-версия в `package.json`: свежие vite и `vue-tsc` требуют современного Node.
  В соседнем проекте `billiards-together` указано `^22.18.0 || >=24.12.0`;
  решение принять в execute, на результат фазы не влияет.
