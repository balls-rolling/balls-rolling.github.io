# CONTEXT — Фаза 03: Диалоги, меню и формы

## Что делает фаза

Строит UI-слой платформы: систему диалогов на нативном `<dialog>`, конструктор
форм по метаданным, экраны меню и интерфейс лобби. Это **функциональная** часть:
вёрстка здесь минимальная (порядок, вертикально/горизонтально, центрирование),
а дизайн и композиция вынесены в отдельную фазу (D11).

**Готово** — значит: есть меню с навигацией и кнопкой «назад», форма настроек с
именем игрока, список игр, преднастройка игры с её собственной формой, интерфейс
лобби объявлен и работает локально, а `test-game` запускается из меню как обычная
игра. Esc и клик вне диалога его не закрывают.

## Принятые решения

### D1. Один диалог со стеком экранов, навигация через менеджер

`DialogManager` владеет одним модальным `<dialog>`. Переход к другому экрану —
особое действие менеджера: предыдущий уходит в историю, старый компонент
скрывается, новый открывается. Кнопка «назад» возвращает из истории. Это не
перерисовка одного экрана, а управляемая навигация.

Реализует решение D13 фазы 02. Отклонено: перерисовка внутри одного экрана
(теряется история и «назад»); несколько диалогов стопкой (браузер закрывает по
Esc только верхний, а нам нужен программный контроль).

### D2. Правила `<dialog>` — из ресёрча фазы 01

- `closedby` ставится **явно всегда**: по умолчанию у `showModal()` это
  `closerequest`, то есть Esc закрывает.
- Поддержка `closedby` (Chrome 134, Firefox 141, Safari preview) не позволяет
  делать его единственным барьером — нужен **второй**: перехват `cancel` через
  `preventDefault()`.
- `showModal()` сам делает всё вне диалога `inert` — ручная блокировка не нужна.
- Для отменяемых действий — `requestClose()`, не `close()`.
- `autofocus` на элемент первого взаимодействия; `tabindex` на `<dialog>` нельзя.
- Анимация: `@starting-style` + `transition-behavior: allow-discrete`, `display` и
  `overlay` в списке `transition` (без `overlay` элемент мгновенно покидает
  верхний слой). `::backdrop` при закрытии не анимируется.

### D3. Главный экран

- **«Играть в "<название>"»** — предыдущая запущенная игра; если её нет, но в
  списке одна игра — она же.
- **«Игры»** — список всех игр.
- **«Настройки»**.

Идентификатор последней игры хранится в глобальных настройках (поле `lastGameId`
рядом с именем игрока). Причина: главный сценарий — «вернуться в игру», он должен
требовать одного нажатия, а не двух.

Отклонено: главный экран с «ИГРАТЬ»/«НАСТРОЙКИ» и списком игр за отдельным
нажатием (лишний шаг для основного сценария).

### D4. Форма строится из метаданных одним конструктором

- Платформа отдаёт **схему**; **один** компонент строит по ней форму и
  возвращает **управляющий объект** (`FormHandle` из фазы 02).
- Расширение контроллов — **реестр рендереров по `kind`**; неизвестный `kind`
  не падает, а показывает запасной вариант.
- Форма не знает ни о чём, кроме того, что в ней есть.

### D5. Модель формы расширяется: группы, текст, контроллы

Элемент формы — не только контролл:

- **Группа** — рекурсивная: содержит элементы формы, включая другие группы.
  - лейбл — необязателен;
  - рамка — есть или нет;
  - ориентация — вертикальная или горизонтальная;
  - схлопываемость — группа может сворачиваться;
  - состояние по умолчанию — свёрнута или развёрнута.
- **Текстовый блок** — строчный или многострочный. Заголовок отдельным
  контроллом не делается: это группа с заголовком.
- **Контролл** — иконка (необязательна), лейбл (необязателен), сам контролл
  (обязателен). Сейчас нужны: кнопка и поле ввода (для имени в настройках).

Заголовок группы — это её лейбл, а не отдельный элемент.

Отклонено: плоский список контроллов без групп (не хватит для преднастройки
сетевых игр); отдельный контролл-заголовок (дублирует функцию группы).

### D6. Ленивые группы — отложены

Схлопываемые группы делаем сейчас. **Ленивые** (отложенное построение детей при
раскрытии, с сигналом и колбэком заполнения, кэшем состояния и правилом «повторное
раскрытие не перегенерирует») — **в бэклог**: у них нет потребителя, ни одна форма
в проекте не настолько тяжёлая, а непроверенный протокол в ядре дороже его
отсутствия. Форма проектируется так, чтобы ленивость добавлялась без ломки:
дети — данные, а не привязанные компоненты.

### D7. Окружение игры: запуск и лобби

Платформа предоставляет игре интерфейс окружения. В нём:

- **запуск игры** — ядро закрывает лишнее, кладёт сессию в свой слот, даёт сигнал
  игровому слою, подключает отрисовку, строит UI;
- **`showHostLobby(options)`** и **`showClientLobby(options)`** — серверное и
  клиентское лобби.

Игра вызывает их **в обработчиках сигналов** от кнопок своей формы. Никаких
флагов «нужна сеть»: игра просто объявляет кнопки, а на их сигналы зовёт нужный
метод.

Полностью заработает, когда появятся отрисовка (фаза 06) и игровой UI (фаза 08).
В этой фазе делается меню, формы, интерфейс лобби и запуск сессии.

### D8. Лобби: интерфейс сейчас, сеть потом

Лобби **серверное и клиентское**, универсальное — рассчитано на **больше двух
игроков**, без флагов «на двоих». В фазе 03 объявляется интерфейс и реализуется
локальная инициализация игроков; сетевая реализация (коды, WebRTC) — фаза 10.

Отклонено: делать лобби целиком сейчас вместе с сетью (сети нет — проверять
нечего); откладывать даже интерфейс (тогда форма преднастройки в 03 получится
заведомо временной).

### D9. `test-game` — обычная игра в списке

Постоянная отладочная панель убирается: тестовая игра появляется в списке игр
наравне с другими и открывается через меню. Меньше шума на экране.

### D10. Технический слой UI отделён от ядра

Ядро не знает о Vue (защищено автотестом фазы 02). Конструктор форм, менеджер
диалогов и экраны живут в `src/ui/**`; ядро отдаёт только метаданные и объекты
управления.

### D11. Дизайн — отдельная фаза сразу после этой

Фаза 03 делает **функционально и с минимальной вёрсткой**: порядок, вертикально и
горизонтально, центрирование. Композиция, отступы, сетка, адаптивность и внешний
вид компонентов проектируются в отдельной фазе дизайна — она встаёт сразу после
03, а следующие фазы сдвигаются на номер.

Причина: смешивать «работает» и «красиво» в одной фазе — значит не закрыть ни то,
ни другое; а вёрстку бессмысленно проектировать до того, как появятся сами экраны.

### D12. Нумерация роадмапа меняется

Дизайн вставляется отдельной фазой после 03. Номера последующих фаз сдвигаются.
Причина: подпапки вида `03-a`/`03-b` ломают определение активной фазы (роутер
берёт наибольший номер без отчёта), поэтому дизайн получает собственный номер.

## Отклонённые варианты

| Вариант | Почему отклонён |
| --- | --- |
| Перерисовка внутри одного экрана вместо навигации | Теряются история и «назад» (D1) |
| Несколько диалогов стопкой | Esc закрывает только верхний; нужен программный контроль (D1) |
| Главный экран с «ИГРАТЬ»/«НАСТРОЙКИ» | Лишний шаг для главного сценария (D3) |
| Плоский список контроллов без групп | Не хватит для преднастройки сетевых игр (D5) |
| Отдельный контролл-заголовок | Дублирует функцию группы с лейблом (D5) |
| Ленивые группы сразу | Нет потребителя, нечем проверить (D6) |
| Флаг `needsLobby` у игры | Игра должна объявлять кнопки, а не флаг (D7) |
| Лобби целиком сейчас с сетью | Сети нет — проверять нечего (D8) |
| Постоянная панель `test-game` | Шум на экране; игра должна открываться из меню (D9) |
| Вёрстка внутри фазы 03 | «Работает» и «красиво» в одной фазе не закрываются (D11) |
| Подпапки `03-a`/`03-b` | Ломают определение активной фазы (D12) |

## Объём фазы

**Делаем:** `DialogManager` с историей и «назад»; конструктор форм (группы
рекурсивные и схлопываемые, текст, кнопки, поле ввода) с реестром рендереров;
экраны главный / список игр / преднастройка игры / настройки; интерфейс лобби с
локальной реализацией; интерфейс окружения игры с запуском и методами лобби;
`test-game` как обычная игра, открываемая из меню.

**Не делаем:** дизайн и композицию (отдельная фаза); сетевое лобби, коды и WebRTC
(10); отрисовку на поле (06); логику крестиков-ноликов (07); ленивые группы
(бэклог).

## Открытые вопросы

- **Стандартный фрагмент формы «игроки и соперник».** По примеру пользователя
  кнопки «1 игрок» / «2 игрока» объявляет сама игра. Стоит ли дать платформе
  готовый переиспользуемый фрагмент, чтобы каждая игра не повторяла его — или
  пока оставить игру один на один с формой.
- **Точный состав окружения игры:** что именно доступно в фазе 03, а что появится
  только с отрисовкой (06) и игровым UI (08). Нужно очертить на plan.
- **Судьба диагностических ярлыков трёх слоёв.** Они заготовка фаз 01–02; после
  появления настоящего меню их место занимает UI. Решить, когда убирать.
- **Форма настроек игры.** Ключ `game/<id>` объявлен решением D6 фазы 02, но пока
  не используется. Экран настроек игры — естественное место закрыть этот хвост;
  нужно решить, входит ли он в эту фазу.
