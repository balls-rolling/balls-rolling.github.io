# CONTEXT — Фаза 05: `Viewport`

## Что делает фаза

Даёт платформе переиспользуемый **canvas-компонент поля**: камера-окно (центр +
масштаб), панорама, зум, учёт `devicePixelRatio`, отсечение видимых клеток,
перевод world↔screen, ввод (drag/wheel/клик) и отладочный оверлей. Это отдельный
инструмент платформы, не привязанный к конкретной игре: тот же компонент покроет
будущий бильярд. Рисование содержимого игры делегируется игре.

**Готово** — значит: в слое поля видно бесконечную сетку, её можно таскать и
зумить (колесо и кнопки), координаты считаются верно при любом dpr, есть
отладочный оверлей с состоянием камеры; математика камеры покрыта тестами без DOM.

## Принятые решения

### D1. Камера — чистая логика в ядре, компонент — тонкая обёртка

Математика камеры (pan, zoomAt, screenToWorld, worldToScreen, visibleBounds,
clamp) живёт отдельным модулем без DOM (`src/core/viewport/camera.ts`) и
тестируется в окружении `node`. Vue-компонент (`src/ui/viewport/Viewport.vue`)
отвечает только за canvas, события ввода, dpr и перерисовку.

Обоснование: ядро платформы тестируется без DOM (решение D4 фазы 02); камера —
чистая функция геометрии, её ошибки ловятся тестами, а не глазами. Отклонено:
вся логика внутри Vue-компонента (нечем проверить без браузера).

### D2. Модель камеры портируется из источника

Берём проверенную модель `tic-board.js`: камера — `{x, y, scale}`, где `(x, y)` —
центр окна в мировых клетках, `scale` — размер клетки в px. Панорама тянет центр
за курсором, зум сохраняет точку под курсором, `screenToWorld` переводит пиксели
клика в мировые координаты. Диапазон масштаба и базовый размер клетки — константы
Viewport (как `BASE_CELL/MIN_SCALE/MAX_SCALE`, `tic-board.js:4`).

Обоснование: `tic-board.js:29,63,87-101` — рабочее решение, проверенное в
источнике. Отклонено: проекция через матрицы (избыточно для 2D-панорамы).

### D3. Сетка — часть платформенного Viewport, фигуры — дело игры

Viewport сам рисует бесконечную сетку (это «хромированная» часть поля и его
визуальный маркер), но **не знает ни одной фигуры**. Содержимое игры приходит
колбэком `render(frame: ViewportFrame)`, который получает уже настроенный
контекст (dpr, трансформация), камеру, границы видимых клеток и перевод
world↔screen. Сетку можно отключить
флагом — бильярду она не нужна.

Обоснование: PROJECT.md:160 «Рисование делегирует игре»; PROJECT.md:268-269
(источник рисовал фигуры в общем компоненте — это выносится в игру); источник
рисует и сетку, и фигуры в одном месте (`tic-board.js:122-146`), но фигуры —
специфика игры. Отклонено: Viewport рисует фигуры сам (платформа узнаёт о
конкретных играх); игра владеет canvas целиком (дублировала бы камеру/dpr/ввод).

### D4. Ввод: панорама, зум, выбор клетки

Порт поведения источника: drag панорамирует с порогом «был ли это клик» (>5 px),
wheel зумит к курсору, кнопки +/- зумируют к центру; одиночный клик без
панорамирования отдаёт world-координаты клетки наружу (pick). Во время
заблокированного ввода (`blocked`) клик-выбор не срабатывает.

Обоснование: `tic-board.js:53-101`. Отклонено: отдельные жесты клавиатурой
(тач-жесты вне v1).

### D5. dpr и отсечение

Канвас пересчитывается под `devicePixelRatio`, контекст получает
`setTransform(dpr, …)`; видимые границы считаются от камеры и размера канваса с
запасом в 1 клетку. Обоснование: `tic-board.js:110-121` — рабочее решение.

### D6. Отладочный HUD — часть платформы

Небольшой переключаемый оверлей внутри Viewport: камера (`x, y`), масштаб, dpr,
размер окна. Это инструмент платформы (принцип 5 PROJECT.md), а не игра.

Обоснование: ROADMAP фазы 05 прямо называет «отладочный оверлей»; PROJECT.md:47-48
«Отладка средствами платформы … часть платформы». Уточнение к D10 фазы 02 (HUD
объединён с `test-game`): тестовый HUD `test-game` остаётся про сессию, а HUD
камеры принадлежит Viewport. Отклонено: HUD только в `test-game` (поле — общий
инструмент, отладка камеры не должна зависеть от игры).

### D7. Монтирование в слой поля, связка с игрой — позже

Viewport монтируется в `LayerBoard` (слой 1) и на этой фазе работает
**самостоятельно**: поле с сеткой, камерой, зумом и HUD, без игровой логики.
Рендер конкретной игры подключается в фазе 07 через колбэк D3; изменения в `Game`
в этой фазе не нужны.

Обоснование: ROADMAP 05 — «бесконечное поле с камерой, зумом и отладочным
оверлеем»; рендер фигур и логика — фаза 07. Отклонено: сразу добавить
`Game.render` (фаза 07 определит контракт по реальной игре, контракт не будет
гадать).

### D8. Цвета поля — из токенов, читаются один раз

Сетка и фон берут цвета из токенов темы; чтение — при монтировании и на смену
темы, а не на каждый кадр. Токены поля (`--board-bg`, `--board-grid`) объявляются
в `tokens.css`; фигурные (`--board-x`, `--board-o`) пока не нужны — появятся с
фигурами.

Обоснование: BACKLOG.md:58 (`tic-board.js:103` — цвета через `getComputedStyle` на
каждом кадре, отмечено как проблема); BACKLOG.md (токены поля — фазы 05/07).
Отклонено: читать цвета каждый кадр (деградация) или хардкодить цвета (ломает
тему).

## Отклонённые варианты

| Вариант | Почему отклонён |
| --- | --- |
| Вся логика камеры в Vue-компоненте | Нечем проверить без DOM (D1) |
| Проекция матрицами | Избыточно для 2D-панорамы (D2) |
| Viewport рисует фигуры | Платформа узнаёт о конкретных играх (D3) |
| Игра владеет canvas целиком | Дублирует камеру/dpr/ввод (D3) |
| HUD только в `test-game` | Отладка поля — общий инструмент (D6) |
| Добавить `Game.render` сейчас | Контракт без реальной игры будет гаданием (D7) |
| Читать цвета каждый кадр | Деградация, отмечено в бэклоге (D8) |

## Объём фазы

**Делаем:** чистую камеру с тестами; `Viewport.vue` (canvas, ввод, dpr, сетка,
отсечение, колбэк рендера, HUD); токены поля; монтирование в `LayerBoard`.

**Не делаем:** логику крестиков-ноликов и ИИ (фаза 06); рендер фигур конкретной
игры и игровой UI (фаза 07); фоновое демо (фаза 08); сеть (фаза 10).
