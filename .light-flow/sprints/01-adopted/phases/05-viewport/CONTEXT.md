# CONTEXT — Фаза 05: `Viewport`

## Что делает фаза

Даёт платформе переиспользуемый **canvas-компонент поля**: камера-окно (центр + масштаб), панорама, зум, учёт `devicePixelRatio`, отсечение видимых клеток, world↔screen, ввод (drag/wheel/клик) и отладочный оверлей. Инструмент платформы, не привязанный к игре (тот же компонент покроет бильярд); рисование содержимого делегируется игре.

**Готово** — значит: в слое поля видна бесконечная сетка, её можно таскать и зумить (колесо и кнопки), координаты верны при любом dpr, есть HUD с состоянием камеры; математика камеры покрыта тестами без DOM.

## Принятые решения (D*)

- **D1. Камера — чистая логика в ядре, компонент — тонкая обёртка.** Математика (pan, zoomAt, screenToWorld, worldToScreen, visibleBounds, clamp) в `src/core/viewport/camera.ts` без DOM, тесты в `node`; `src/ui/viewport/Viewport.vue` — только canvas/ввод/dpr/перерисовка. Ядро тестируется без DOM (D4 фазы 02). Отклонено: вся логика в Vue (нечем проверить без браузера).
- **D2. Модель камеры портируется из источника.** `tic-board.js`: `{x,y,scale}`, `(x,y)` — центр окна в мировых клетках, `scale` — px/клетка; панорама тянет центр, зум сохраняет точку под курсором; константы BASE_CELL/MIN_SCALE/MAX_SCALE (`tic-board.js:4`). Источник `tic-board.js:29,63,87-101`. Отклонено: проекция матрицами (избыточно для 2D).
- **D3. Сетка — часть платформенного Viewport, фигуры — дело игры.** Viewport рисует бесконечную сетку, но не знает фигур; содержимое приходит колбэком `render(frame: ViewportFrame)` (готовый контекст с dpr, камера, границы, world↔screen); сетку можно отключить. Обоснование PROJECT.md:160,268-269. Отклонено: Viewport рисует фигуры; игра владеет canvas целиком.
- **D4. Ввод: панорама, зум, выбор клетки.** drag панорамирует с порогом «был ли клик» (>5px), wheel зумит к курсору, кнопки ± к центру, одиночный клик отдаёт world-клетку (pick); при `blocked` pick не срабатывает. Источник `tic-board.js:53-101`. Отклонено: отдельные жесты клавиатурой (тач-жесты вне v1).
- **D5. dpr и отсечение.** Канвас пересчитывается под `devicePixelRatio`, `setTransform(dpr,…)`; видимые границы от камеры и размера с запасом 1 клетка (`tic-board.js:110-121`).
- **D6. Отладочный HUD — часть платформы.** Переключаемый оверлей внутри Viewport: камера (`x,y`), масштаб, dpr, размер окна. Принцип 5, ROADMAP 05, PROJECT.md:47-48. Уточнение к D10 фазы 02: HUD `test-game` — про сессию, HUD камеры — Viewport. Отклонено: HUD только в `test-game`.
- **D7. Монтирование в слой поля, связка с игрой — позже.** Viewport в `LayerBoard` (слой 1), работает самостоятельно; рендер игры — фаза 07 через D3; изменения в `Game` не нужны. Обоснование: ROADMAP 05; рендер/логика — 07. Отклонено: сразу добавить `Game.render`.
- **D8. Цвета поля — из токенов, читаются один раз.** Сетка/фон из токенов; чтение при монтировании и на смену темы, не каждый кадр. Токены `--board-bg`/`--board-grid` в `tokens.css`; фигурные (`--board-x`/`--board-o`) позже. Обоснование BACKLOG.md:58 (`tic-board.js:103`). Отклонено: читать каждый кадр / хардкод.

## Отклонённые варианты

| Вариант | Почему отклонён |
| --- | --- |
| Вся логика камеры в Vue-компоненте | Нечем проверить без DOM (D1) |
| Проекция матрицами | Избыточно для 2D-панорамы (D2) |
| Viewport рисует фигуры | Платформа узнаёт о конкретных играх (D3) |
| Игра владеет canvas целиком | Дублирует камеру/dpr/ввод (D3) |
| HUD только в `test-game` | Отладка поля — общий инструмент (D6) |
| Добавить `Game.render` сейчас | Контракт без реальной игры — гадание (D7) |
| Читать цвета каждый кадр | Деградация, отмечено в бэклоге (D8) |

## Объём фазы

**Делаем:** чистую камеру с тестами; `Viewport.vue` (canvas, ввод, dpr, сетка, отсечение, колбэк рендера, HUD); токены поля; монтаж в `LayerBoard`.
**Не делаем:** логику крестиков-ноликов и ИИ (06); рендер фигур и игровой UI (07); фоновое демо (08); сеть (10).
