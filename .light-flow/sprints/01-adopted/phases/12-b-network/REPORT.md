### Хранилище: фолбэк IndexedDB → localStorage (по тесту заказчика)

Наблюдение: в браузере заказчика IndexedDB пустая, сохранения не пишутся, на главном нет «Продолжить» (локальная партия тоже не сохранялась). Причина: `createIdbStore` брал IndexedDB при наличии API и **глушил** ошибки открытия/записи, запасного пути не было.

Исправлено (`src/core/storage/backends.ts`, `idb.ts`, `store.ts`):
- `FallbackBackend` — операции идут в основной бэкенд, при первом сбое «защёлка» переводит всё на запасной (localStorage, при недоступности — память); консистентно в рамках сессии.
- `createIdbStore` = IndexedDB + (`localStorage` или память) через `FallbackBackend`.
- Таймаут открытия IndexedDB (4 с) — «зависшее» открытие (некоторые сборки Safari) уводит хранилище в запасной бэкенд.

Проверено: тесты `store.test.ts` (сбой основного → запасной; `createIdbStore` без IndexedDB сохраняет). Браузерно (init-скрипт с `indexedDB = undefined`): сохранение легло в `localStorage` (`mini-games:game/tic-tac-toe`), после перезагрузки на главном — «Продолжить «Крестики-нолики»».

**Уточнение (повторный тест заказчика):** имя игрока (localStorage) переживало перезагрузку, а сессия не сохранялась. Причина — **зависший старый dev-сервер на `localhost:5173`**, отдававший прежний код; после перезапуска локальное сохранение и «Продолжить» заработали и с IndexedDB. Дополнительно `createIdbStore` получил `FallbackBackend` (IDB → localStorage → память) и таймаут открытия. Сохранения **остаются в IndexedDB** (решение 12-a не менялось).

**Известное ограничение (тест «сам с собой»):** хост и гость в **одном браузере** делят origin-хранилище (одна IndexedDB/localStorage), поэтому снимок хоста затирается действиями гостя. В реальности хост и гость — разные устройства/браузеры, конфликта нет. Сетевой сценарий вживую не проверялся (WebRTC 0 ICE).

**Перезапись снимка — только на старте партии.** Снимок удаляется лишь при явном выходе (`GameMenu`) и при завершении партии; вход в преднастройку его не трогает, а перезапись — в момент `environment.launch` (старт новой сессии). Плюс исправлено: присоединение по приглашению (`options.net`) больше не показывает предупреждение D6 «незавершённая партия может быть потеряна».

**Идентичность гостя при восстановлении (по тесту заказчика).** В preset-лобби хост допускает только ожидаемые id; если гость присылал id хоста (`p1`), его подключение молча игнорировалось (отсюда «ничего не произошло»), а повторный `accept` давал «плохой код ответа». Исправлено: гость выводит свой id из id хоста (`guestIdFor`: хост `p1` → гость `p2`, иначе `p1`), а не берёт жёстко; повторный `accept` в лобби восстановления запрещён (флаг `accepted`). Тест `src/ui/lobby/restore.test.ts`.

## Доработка D16–D20 (постоянный id игрока, уточнение заказчика)

- **Постоянный id игрока.** `GlobalSettings.playerId` (UUID) генерируется при первом чтении настроек, хранится до очистки, переживает сохранение настроек. Главный локальный игрок получает этот id; остальные локальные — `guest_N` (`players.ts`). Сетевые игроки шлют свой постоянный id (`join`/приглашение), и хост-состав идёт первым.
- **Роль по позиции.** `isPersistable`, `networkRole`, `resumeNetworkHost`, `recoverNetworkHost` определяют хоста как `players[0]`, а не по строке `p1`.
- **Восстановление по id.** Preset-состав — это сохранённые игроки с их постоянными id; `join` гостя допускается, только если его id есть среди ожидаемых (иначе отказ). `LobbyRoster` хранит id хоста и проверяет допуск по id.
- **Обрыв у всех.** `WebRtcTransport` переводит `disconnected`/`failed` (`connectionState` и `iceconnectionState`) в состояние обрыва, поэтому `NetRecovery` показывает диалог и у хоста, и у гостя.
