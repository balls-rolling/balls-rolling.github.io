# CONTEXT — Фаза 12: сохранение и восстановление партии

## Что делает фаза

Партия фиксируется после каждого хода; незаконченную можно продолжить с главного
(«Продолжить «<игра>»»). Сетевая партия восстанавливается через лобби с тем же
составом (по id) и повторным обменом ссылкой. Завершённая партия не предлагается;
сохранение удаляется при завершении и при явном выходе. В настройках — очистка
сохранённых игр (по списку) и полный сброс данных.

**Готово** — значит: можно уйти в середине партии (в т.ч. перезагрузить вкладку) и
вернуться в неё одним действием; завершённая не предлагается; сетевой сценарий
восстанавливает прежний состав; в настройках работают очистка и сброс.

Сегодня: `Session` живёт только в памяти, `GameState` не сериализуется (в
крестиках-ноликах камни — `Set<string>`, JSON его теряет), «Продолжить» нет,
IndexedDB нет.

## Принятые решения

### D1. Три подфазы

- **12-a** — локальное сохранение и восстановление;
- **12-b** — сетевое восстановление;
- **12-c** — управление/очистка сохранений (**последний** этап).

Причина: объём больше лимита 10 задач; экраны очистки по просьбе пользователя
идут после функциональности.

### D2. Сериализацию реализует игра (снимок, не реплей)

Платформа не разбирает `GameState`: игра реализует сериализацию/десериализацию
своего состояния. Ключевые данные — очки игроков, чей ход, состояние игрового
поля и т.п. Сессия сериализует и восстанавливает свои данные (игроки и их
свойства, очередь хода, статус, победитель). Отклонён реплей ходами: случайность
ИИ и рост списка ходов на бесконечном поле.

### D3. Хранилище — IndexedDB, древовидное по `id` игры

Единое хранилище. Узел игры `game/<id>` содержит **настройки игры** и
**прерванную партию** (снимок конкретной сессии). `KeyValueStore` уже
асинхронный — переход на IndexedDB не меняет вызывающий код. Точная схема
ключей/записей — на plan.

### D4. Настройки игры и снимок сессии — раздельно

Настройки игры (уровень ИИ и т.п.) живут в узле игры и **переживают партии**;
снимок конкретной сессии — отдельная часть того же узла, удаляется при
завершении/выходе. Это закрывает хвост «игровые свойства не персистятся»
(механизм хранения). Экран настроек игры/рейтинга в объём фазы **не входит**.

### D5. Автосохранение после изменения; демо не сохраняется

Фиксация — по подписке на изменение сессии (после каждого принятого хода).
Демо-сессии не сохраняются.

### D6. Хранится каждая незаконченная партия

Слот не один: у каждой игры свой узел с её прерванной партией. При старте новой
партии той же игры поверх сохранённой — **предупреждение**, что предыдущая может
быть потеряна.

### D7. Удаление: завершение и явный выход

Сохранение удаляется при завершении партии и при явном выходе в меню.
Перезагрузка/закрытие вкладки **не** удаляет — иначе «Продолжить» бессмысленно.

### D8. «Продолжить» на главном

Если у игры есть прерванная партия, на главном — «Продолжить «<игра>»»; иначе
обычный запуск.

### D9. Сетевое восстановление (12-b)

Хост поднимает сохранённую партию и открывает **лобби восстановления**: состав
предопределён (те же id/имена), приглашение — свежая ссылка/QR, гость
подключается и сверяется по id. Старт — по кнопке хоста (без автостарта, как
фаза 11 D3). SDP — свежий (ICE-restart); старые каналы не переиспользуются.

### D10. Управление сохранениями (12-c)

В настройках две кнопки:

- **«Стереть все данные»** — полностью очищает хранилище (включая глобальные
  настройки) и перезапускает страницу; активна только при наличии сохранённых
  данных;
- **«Очистить сохранённые игры»** — диалог со списком сохранённых игр, выбор что
  удалить/оставить; активна только при наличии сохранённых игр.

## Отклонённые варианты

| Вариант | Почему отклонён |
| --- | --- |
| Реплей ходами вместо снимка | Случайность ИИ и рост списка ходов на бесконечном поле (D2) |
| Один слот на всё | Пользователь: хранить каждую незаконченную партию (D6) |
| Настройки игры внутри снимка сессии | Пользователь: настройки игры и сессия — раздельно (D4) |
| Переиспользовать прошлые SDP | Мёртвые каналы; нужен свежий обмен/ICE-restart (D9) |
| Удалять сохранение при закрытии вкладки | Ломает саму цель восстановления (D7) |

## Допущения (проверить на plan)

- Точная схема IndexedDB: имя БД/стора, ключи, форма узла игры.
- Сетевой случай 12-b, когда вернулись не все игроки (продолжить нельзя) и судьба
  сохранения при отмене лобби восстановления.
- Миграции снимка при смене версии схемы (использовать существующий конверт с
  версией).

## Открытые вопросы

Нет — решений достаточно; уточнения выше уходят в ресёрч этапа plan.

## Разбиение на подфазы

- **12-a — локальное сохранение и восстановление.** Контракт сериализации
  (`Game` + сессия), IndexedDB-хранилище по узлам игры, автосохранение после
  хода, восстановление, «Продолжить» на главном, удаление при завершении и явном
  выходе, предупреждение при старте новой партии поверх сохранённой.
- **12-b — сетевое восстановление.** Лобби восстановления с предопределённым
  составом, повторный обмен ссылкой/QR, сверка по id, старт по кнопке хоста,
  свежий SDP/ICE-restart.
- **12-c — управление сохранениями.** «Стереть все данные» и «Очистить
  сохранённые игры» (диалог со списком) в настройках.

CONTEXT общий для всех подфаз; обсуждение проводится один раз.

## Дополнение (уточнение замысла после ручного теста, 2026-10-04)

Реализация 12-b отклонилась от замысла. Правильное поведение сети:

- **D11. Сетевую партию помнит и восстанавливает только хост.** Гость снимок не
  хранит и кнопки восстановления не имеет; он «просто подключается как обычно».
- **D12. При обрыве у гостя — диалог о проблеме.** Механизм восстановления есть
  (хост инициирует), поэтому у гостя окно переподключения (ждать новую ссылку
  хоста) с кнопкой «Покинуть игру».
- **D13. При обрыве у хоста — диалог «соперник отключился»** с действием
  «Восстановить» (открывает лобби восстановления со свежей ссылкой) и «Покинуть».
- **D14. Состояние передаёт хост.** После переподключения канала хост шлёт гостю
  снимок своей партии (новое сообщение протокола); гость принимает его и
  продолжает с той же позиции. Гость локально снимок не хранит.
- **D15. Восстановление инициирует только хост**, старт — по его кнопке, состав по
  тем же id (как в лобби).

Следствия для кода: `isPersistable` сохраняет сетевые сессии **только у хоста**
(локальный игрок `p1`); путь восстановления гостя по локальному снимку не
используется — гость подключается заново и получает состояние от хоста.

## Дополнение 2. Идентичность игроков (уточнение после тестов)

- **D16. Постоянный id игрока.** У главного игрока устройства — постоянный id
  (UUID), генерируется при первом чтении настроек и хранится до очистки данных
  (`GlobalSettings.playerId`). Прочие **локальные** игроки (второй человек за
  экраном, компьютеры) получают временные id вида `guest_N`.
- **D17. Сетевые игроки шлют свой id.** Хост и гость передают свои постоянные id
  в приглашении/`join`/`hello`; состав ведёт хост, порядок — хост первым.
- **D18. Восстановление по id.** При восстановлении подключающийся занимает место
  того же игрока **по его постоянному id**; чужому — отказ с сигналом, что он не
  может подключиться.
- **D19. Роль по позиции, не по id.** Хост — первый в составе (`players[0]`);
  `isPersistable`/роль определяются этим, а не строкой `p1`.
- **D20. Обрыв виден всем оставшимся.** При аварийном обрыве (`connectionState`/
  `iceConnectionState` `disconnected`/`failed`) уведомление о прекращении сессии
  получают **все** оставшиеся, а не только гость.
