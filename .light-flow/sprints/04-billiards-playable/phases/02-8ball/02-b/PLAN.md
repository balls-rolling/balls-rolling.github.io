## Цель и объём

Партия 8-ball за одним экраном: игрок выбирает режим, правила и способ старта,
играет с движимым битком, видит переход хода, шкалы забитых и экран результата.
Ядро правил из 02-a не переписывается — достраивается **передача хода** и
поверхности UI.

«Готово» — локальная партия «двое за экраном» проходится целиком руками
(живьём): правила и результат видны, биток после фола двигается без
пересечений, между ударами поле не трогается, рейки не залезают под панели.

**Не входит:** ИИ (`chooseShot` → `null`, 02-c), обмен ударами по проводу
(02-d). Кнопки «с компьютером» и «по сети» появятся и доведут до стола, но партия
в них не доигрывается — это ожидаемо и будет сказано на проверке.

## Задачи

1. **Преднастройка двумя шагами: режим → параметры и запуск.** **Требование**
   (пользователь, 2026-10-16): первый экран — выбор режима, после выбора —
   экран параметров этого режима и кнопки старта, доступные в режиме
   («2 локально» / «с компьютером» / «по сети»). Форма игры статична и
   создаётся один раз (`src/main.ts:87`, `controller.ts:17`), поэтому шаги —
   две группы-«схлопывашки» одной формы: «Шаг 1. Режим» (select `mode`) и
   «Шаг 2. Параметры и запуск» (select `rules`: простые/турнирные +
   кнопки старта). Образец — форма tic-tac (`src/games/tic-tac/game.ts:44-124`).
   `attachEnvironment` запускает нужным составом: `defaultPlayers({humans:2})`,
   `defaultPlayers({humans:1, computers:1})`, `lobby.showHost()/showClient()`
   (`tic-tac/game.ts:174-225`). Имена игроков игра собирает сама для плашки хода и
   результата. Правила из формы идут в состояние партии (поле `state.rules`,
   02-a) — второго источника не заводим. Сеть здесь — только лобби и запуск.
   Файлы: `src/games/billiards/game.ts`. Зависимости: нет. **Тесты: да**
   (схема формы, состав по каждому способу старта, правила попадают в состояние).
   *Done:* форма содержит выбор режима и выбор правил; нажатие каждой из трёх
   кнопок старта приводит к `environment.launch` с составом «двое люди»,
   «человек + компьютер», составом лобби; выбранные правила видны в состоянии
   новой партии.

2. **Передача хода: следующий ход с параметрами.** **Требование** (пользователь,
   2026-10-16): разбор лога предыдущего удара определяет начальные условия
   следующего — кто ходит, причина перехода (фол / забил свой / забил чужой /
   разбитие / партия окончена) и особенности подготовки (можно ли позиционировать
   битка, можно ли выбирать биток). Следующий ход начинается с этими
   параметрами. Значит: разбор правил отдаёт передачу хода (игрок + причина +
   права подготовки), а поле между ударами не трогается — **биток появляется
   только на подготовке следующего хода** (CONTEXT «Цикл хода»), а не сразу в
   `resolveShot`. Фазы хода (подготовка → симуляция+реплей → обработка →
   передача → подготовка) живут в игре, несериализуемы, ввод блокируется вне
   подготовки.
   Файлы: `src/games/billiards/rules-8ball.ts` (передача хода из разбора),
   `src/games/billiards/state.ts` (сериализуемая часть: причина/флаги подготовки —
   чтобы сеть и сохранение 02-d/08 воспроизвели ход), `src/games/billiards/game.ts`
   (фазы, блокировка ввода, появление битка на подготовке).
   Зависимости: нет. **Тесты: да.**
   *Done:* удар с фолом через публичный `Game` даёт передачу хода сопернику с
   причиной «фол» и правом позиционировать биток; между фазами «обработка» и
   «передача» биток на столе не появляется, а появляется в фазе «подготовка» в
   разрешённой точке; после легального забитого своего передача тому же игроку с
   причиной «забил свой» и без права позиционировать.

3. **Плашка перехода хода.** **Требование** (CONTEXT п.6 цикла хода): между
   ударами над столом показывается, чей ход и почему он перешёл, включая «тот
   же игрок, продолжает». Готового механизма в проекте нет; решение — локальный
   оверлей в `BilliardsUi.vue`, управляемый фазой из задачи 2 и именем игрока
   из задачи 1 (платформу не расширяем, §9/D12).
   Файлы: `src/ui/games/billiards/BilliardsUi.vue` + метод игры «фаза/передача».
   Зависимости: 1, 2. **Тесты: живьём.**
   *Done:* живьём — после удара, сменившего ход, плашка показывает имя следующего
   игрока и исчезает к началу прицеливания; при продолжении хода плашка
   показывает «продолжает»; плашка не перекрывает зону ввода и стол.

4. **Движимый биток на подготовке (с руки).** **Требование** (CONTEXT п.6):
   биток ставится на начало хода, затем игрок, чей ход, двигает его по столу и

   уже умеет перетаскивание (`BilliardsUi.vue` `placeCueAt`/`startMove`) — пускаем

   Файлы: `src/games/billiards/game.ts`, `src/ui/games/billiards/BilliardsUi.vue`.
   Зависимости: 2. **Тесты: да** (ядро) + **живьём** (перетаскивание).

## Забыто

- **«С компьютером» и «по сети» неиграбельны сейчас** (`chooseShot` → `null`,
  протокол не несёт удар). Кнопки доводят до стола; партия встанет на ходе
  компьютера/удалённого. Озвучить на проверке, не «чинить».
- **Имена игроков** игра собирает сама; их нет ни в состоянии, ни в форме — нужны
  плашке хода и результату.
- **Правила идут одним путём** `форма → игра → state.rules`; второй источник
  (настройки экземпляра и состояние) не заводим.
- **Открытый стол и шкалы:** до назначения групп атрибуции нет — допущение
  «забитые на стороне бьющего».
- **Право размещения битка** = подготовка ∧ (рука ∨ свежая партия) ∧ ход
  человека; на ходе компьютера/во время реплея/плашки — запрещено.
- **Плашка — локальный оверлей**, не зона платформы: зоны декларативны, платформу
  не расширяем.
- **Форма не подставляет сохранённые настройки в контроллы** (значение зашито в
  схеме) — то же ограничение, что у tic-tac; не расширяем, отмечаем.
- **Два шага сделаны схлопывающимися группами одной формы**, потому что схема
  статична (`src/main.ts:87`, `core/form/controller.ts:17`). Настоящий модальный
   шаг потребовал бы пересборки схемы платформой — цена осознанно не платится,
   пока режим один.
- **Нормы §4 (сила, fit) уже покрыты** тестами; здесь добавляются только живые
   нормы (курсоры, стабильность геометрии без второй панели, отсутствие
   отладочных элементов).

## Риски

- **Фазы хода против состояния сессии:** `draw` получает состояние сессии каждый
  кадр, а фазой рулит игра. Ошибка порядка даст залипшую фазу — ловят задача 2
  (тест фаз) и задача 3 (живьём).
- **Заблокированный ввод:** плашка/фаза не должны оставить UI без хода, особенно
  на ходе компьютера без ИИ — проверка живьём.
- **Рейки/инсеты — общий код зон:** правка затрагивает `test-game` и крестики;
  регресс зон и `fit/render.test.ts` обязателен.
- **Скачок конца хода:** все ветки `draw` должны брать один набор параметров вида
  и фазы (`ui-behavior.md` п.7) — задачи 2 и 7.
- **Разные пути ввода битка** (перетаскивание, стартовая позиция, удар) обязаны
  давать один результат — задача 4.
- **Форма — статичная схема:** шаги схлопывашками; при появлении второго режима
  (06) шаг 1 перестанет быть формальностью — проверить тогда.
- **Результат при простых правилах:** неправильная 8 не завершает партию, текст
  результата не должен обещать поражения.

## Решения

- **Образец — tic-tac** (форма с кнопками и сетью, `#names`, `#showResult`,
  `serializeSettings`): `src/games/tic-tac/game.ts`. Цена: 0.
- **Шаги настройки — схлопывающиеся группы одной формы** вместо пересборки
  схемы платформой. Цена: при одном режиме шаг 1 формален.
- **Плашка перехода — локальный оверлей** в UI игры, не платформенный механизм.
  Цена: игра отдаёт фазу и имя.
- **Передача хода — результат разбора правил**, а не отдельная логика UI: один
  источник истины для сети/сохранения. Цена: состояние растёт полем причины и
  флагов подготовки.
- **Запрет пересечений — существующее мягкое выталкивание** `withPlacedCue`, не
  второй валидатор. Цена: при плотной постановке биток мягко сдвигается.
- **Внешних библиотек нет.** Цена: только время.
