Статус: **утверждено пользователем 2026-10-17**. Исполняется. Наследует `../CONTEXT.md` (решения пп. 4–5, 10; раздел «Цикл хода» — обязателен) без повторного обсуждения.

## Цель и объём

Две стороны по ссылке играют партию 8-ball: ход идёт через уже существующий `Transport` (лобби спринта 01), удар передаётся **непрозрачным payload игры**, результат удара сопровождается `hash` + `shotSeq`, хост — источник правды при рассинхроне. Партия не залипает на смене хода, удалённый игрок не путается с компьютером.

**Не входит:** контрольная сумма `Invite` (§8:247–249) — в «Отложено»; игровой реванш в `Session` (только лобби); спин/точка удара (фаза 07); safety play.

**Живой WebRTC не проверить (0 ICE, §8:252–253):** все проверки — тесты и парные фейк-транспорты. Это «не проверено живьём» в каждом done-условии.

## Задачи

1. **Удар идёт по сети как непрозрачный payload игры.** **Требование** (§8:243; CONTEXT п.5). Сейчас протокол зашит на `{t:"move",x,y}` и диспетчер требует целые `x,y` (`protocol.ts:10,39-43`), а мост кладёт `{x,y}` (`link.ts:125-129,89`). Обобщить: сообщение несёт поле-объект игры (`{t:"move", m: Move, seq?, hash?}`), ядро/протокол состав удара **не разбирают**; `NetApi.remoteMove` принимает `Move` и метаданные, `sendMove` шлёт объект. Крестики-нолики не должны сломаться: их `Move` — те же `{x,y}` внутри `m`. Регресс — существующие тесты `ui/net/link.test.ts`, `core/net/net.test.ts` (обновить под новый формат).
   Файлы: `src/core/net/protocol.ts`, `src/ui/net/link.ts` (+ их тесты), при необходимости `src/ui/games/tic-tac/TicTacToeUi.vue`.
   Зависимости: нет. **Тесты: да.**
   *Done:* любая форма `Move` проходит через протокол и доходит до `session.makeMove` без разбора ядра; мусор (`m` не объект) отбрасывается молча; крестики-нолики играют сетевую партию как раньше.

2. **Сетевой мост бильярда в UI: подключение, роли, реплей входящего удара.** **Требование** (§8:241–242; CONTEXT п.5, «Цикл хода»). Бильярдный UI сеть не использует вовсе (grep `netLink` по `src/ui/games/billiards` — 0). По образцу `TicTacToeUi.vue:20-22,36`: инжектить `netLinkKey`, при наличии транспорта `attach(session)`; роль хост/гость — по `transport` игрока (образец `ui/net-recovery.ts` `networkRole`), хост задаёт `outgoingState` (`link.ts:18,113-117`). Ключевое отличие от tic-tac: **входящий ход должен проигрываться реплеем, а не применяться мгновенно**. Сейчас `link.ts:89` зовёт `session.makeMove` напрямую — поле телепортируется, цикл хода обходится. Механизм — хук входящего хода в `NetLink` (кандидаты в «Решениях»); логику вынести в тестируемый модуль, а не в `.vue`.
   Файлы: новый `src/ui/games/billiards/net.ts` (мост), `src/ui/games/billiards/BilliardsUi.vue` (инжект и вызовы `beginShot`/отправка), `src/ui/net/link.ts` (хук).
   Зависимости: 1. **Тесты: да** + **не проверено живьём** (WebRTC).
   *Done:* на парных фейк-транспортах удар стороны A доходит до B и проигрывается реплеем (поле не телепортируется); гость снимок не шлёт; хост шлёт снимок на `hello`/`open`.

3. **Результат удара: hash + shotSeq, shooter-authoritative, идемпотентность.** **Требование** (§8:242; ресёрч §3). После локального применения удара отправитель прикладывает `shotSeq` и `hashBilliardsState(nextState)` (`state.ts:353-355`; канон уже включает `shotSeq` :383, `version/mode/seed/order/turn/...`). Приёмник после реплея применяет ход тем же путём (`session.makeMove` → `applyShotWithLog`, `game.ts:514`) и **сверяет свой хеш**; состояние берётся из `makeMove`, а не из визуального реплея (иначе расхождение путей симуляции). Идемпотентность: `shotId = (matchId, shotSeq, shooterId)`, `lastAppliedSeq` на отправителя; дубликат/старый seq — no-op; неупорядоченный — буфер.
   Файлы: `src/ui/games/billiards/net.ts`, `src/games/billiards/state.ts` (при необходимости экспорт `hashBilliardsState` — уже экспортирован).
   Зависимости: 1, 2. **Тесты: да.**
   *Done:* повторный/устаревший `shotSeq` не меняет состояние; хеш приёмника равен хешу отправителя на детерминированном ударе; при расхождении — сигнал ресинка (задача 4).

4. **Ресинк: расхождение хеша или `hello` → снимок хоста.** **Требование** (§8:242; CONTEXT п.4). Переиспользовать существующий `sync`/`adoptState` (`protocol.ts:47-49` → `link.ts:91-93` → `session.adoptState`, `session.ts:170-195`). При расхождении хеша гость просит снимок, хост отвечает `sync` (`outgoingState = () => session.save()`); гость `adoptState`. `adoptState` десериализует состояние, но рантайм анимации игры не трогает — после ресинка вызвать `resetRuntime()` (`game.ts:842`), иначе кадр останется от прежнего удара.
   Файлы: `src/ui/games/billiards/net.ts`, `BilliardsUi.vue`, `link.ts` (сообщение-запрос при необходимости).
   Зависимости: 3. **Тесты: да.**
   *Done:* искусственно вызванное расхождение → гость принимает снимок хоста, поле и очередь совпадают с хостом, партия продолжается без залипания; хост — правда.

5. **Параметры партнёру при старте: режим + правила + seed (+ сложность).** **Требование** (CONTEXT п.4, §8). Хост шлёт стартовый снимок; `gameState` уже несёт `mode/rules/seed` (`state.ts:63-66`), а сложность живёт вне `gameState` (`game.ts:1098-1104`) — в сетевой партии ИИ нет, но настройку приложить для верности. Гость до первого хода принимает параметры хоста и не может стартовать с расходящимися правилами. Порядок игроков на обеих сторонах совпадает (хост первым — лобби уже так строит, `ui/lobby/net.ts:88-101,255-263`) — проверить тестом, от него зависит `state.order`/`turn`.
   Файлы: `src/ui/games/billiards/net.ts`, `link.ts` (состав `sync`), `game.ts` (доступ к `serializeSettings`).
   Зависимости: 4. **Тесты: да.**
   *Done:* после старта `mode/rules/seed` гостя равны хостовым; `order` совпадает; гость, выбравший другие правила, играет по хостовым.

6. **Смена хода с удалённым игроком: не путать с компьютером, без залипания.** **Требование** (§8:244; CONTEXT «Цикл хода»). Удалённый игрок — `agent:"human"`, `transport:"remote"` (`player.ts:8-11`), поэтому `currentPlayerIsComputer()` (`BilliardsUi.vue:155-160`) его **не** ловит, но и ввод человека по нему сейчас не гейтится: `shoot()` блокирует только `computerTurn` (:525). Гейт ввода — «текущий игрок — мой локальный человек»; на ходе удалённого ввод заблокирован. Очередь не чередуется: возврат хода тому же игроку (`pottedOwn`) — по `state.turnReason`/`nextPlayer`, не по чётности. После удалённого удара — реплей → плашка → `acknowledgeTurn` → разблокировка, если ход снова локальный; серия ходов удалённого не должна залипать.
   Файлы: `src/ui/games/billiards/BilliardsUi.vue`, `src/ui/games/billiards/net.ts`.
   Зависимости: 2. **Тесты: да** + **не проверено живьём**.
   *Done:* на ходе удалённого игрока ввод локального заблокирован, компьютерный путь не запускается; после удалённого удара показан реплей и плашка, затем ввод разблокирован по правилам; возврат хода тому же игроку не залипает.

7. **Интеграционный тест: две стороны играют партию до конца.** **Требование** (§8; CONTEXT «Проверяемо»). Два `Session`+моста, соединённые парным фейк-транспортом (образец `link.test.ts:7-35`, `session.test.ts:34-40`), играют 8-ball до победителя; финальные хеши обеих сторон равны; нет зависаний и повторного применения. Проверить идемпотентность (дубликат), ресинк (сбойный удар) и смену хода.
   Файлы: тесты `src/ui/games/billiards/*.test.ts` (парный фейк-транспорт).
   Зависимости: 1–6. **Тесты: да.**
   *Done:* партия завершается за конечное число ударов с победителем; `hashBilliardsState` финальных состояний совпадает на обеих сторонах; дубликат хода не меняет состояние; искусственный рассинхрон разрешается снимком хоста.

## Забыто (что несут задачи неявно)

- **Хук входящего хода в `NetLink`** — без него сеть бильярда применяет удар мгновенно, минуя реплей (задача 2). Это расширение платформенного UI-моста.
- **`outgoingState` для бильярда** сейчас задаёт только `resume-net-game.ts:40`; в новой сетевой партии его надо подключить, иначе `sync`/ресинк отсутствует (задачи 2, 4).
- **`resetRuntime()` после `adoptState`** — `deserializeState` ставит `#lastState`/`preparing`, но не чистит `#runtime`/`#lastFinished` (`game.ts:842-852`); без сброса кадр от прежнего удара (задача 4).
- **Порядок игроков совпадает на обеих сторонах** (хост первым) — от него зависят `state.order`/`turn`; лобби уже так строит, закрепить тестом (задача 5).
- **`shotSeq` уже в состоянии и в каноне хеша** (`state.ts:88-89,383`); `matchId` — из `seed` (задача 3).
- **Удалённый игрок ≠ компьютер:** `agent` и `transport` — разные поля (`player.ts`); гейт ввода по обоим (задача 6).
- **Результат удара берётся из `makeMove`, а не из реплея** — обе стороны применяют один путь `applyShotWithLog`, иначе хеши разойдутся (задача 3).
- **Сложность вне `gameState`** (`game.ts:1098-1104`) — приложить к старту отдельно или явно зафиксировать неприменимость без ИИ (задача 5).
- **Гость снимок не шлёт** — `outgoingState` только у хоста (задача 2).
- **Контрольная сумма `Invite` (§8:247-249)** — вне объёма, в «Отложено».

## Риски (проверяются на verify)

- **Ложный ресинк из-за расхождения путей симуляции:** реплей (`startShot`+`advance`) и применение (`applyShotWithLog`) могут дать микрорасхождение → хеш не сойдётся, петля ресинков. Митигация — хеш из `makeMove`, реплей только визуальный (задача 3); ловится тестом 7.
- **Хеш включает сырые float** (`canonicalStateString` :361) — на одной платформе детерминирован, кросс-платформенно не гарантирован; ресёрч советует квантованное дискретное состояние. Отметить; в рамках одной платформы риск низкий.
- **Залипание `passing`** на удалённом ходе (как в 02-c на компьютерном) → поле мёртво; задача 6, тест 7.
- **Регресс `protocol.ts`/`link.ts`** — обобщение `move` ломает `net.test.ts`, `link.test.ts`, tic-tac; обновить их (задача 1).
- **Двойная отправка/применение** при гонке реплея и приёма — идемпотентность по `shotId`/`lastAppliedSeq` (задача 3).
- **`adoptState` не сбрасывает рантайм** → визуальный мусор после ресинка (задача 4).
- **Несовпадение `order`** → ход уходит не тому, `makeMove` отклоняется, партия встаёт; проверка порядка (задача 5).
- **Реванш по сети** — игрового `rematch` в `Session` нет (только лобби, `lobby-protocol.ts:18-20`); новая партия = новый seed/matchId, сброс `shotSeq`. Вне объёма — «Отложено».
- **QR/`Invite` не растёт** — метаданные не добавляем (checksum отложена), риск размера снят.
- **Живой WebRTC не проверен** — только фейки; интеграция в браузере остаётся неподтверждённой (в done-условиях).

## Решения

- **Обобщить `move` до непрозрачного `m: Move`** аддитивно, по ресёрчу §3 («`Move` уже непрозрачен, обобщение аддитивно»). Цена: правки общего протокола и тестов tic-tac/link.
- **Хук входящего хода в `NetLink`** (вместо прямого `session.makeMove`), чтобы игра сама решала, играть ли реплей. Кандидаты: (а) `NetLinkConfig.onRemoteMove(move, meta)`; (б) `NetLink.setRemoteMoveHandler(fn)` с фолбэком на `session.makeMove`. Цена: расширение платформенного UI-контракта (минимальное, §9 «платформенный код трогаем минимально»).
- **Ресинк — существующим `sync`/`adoptState`** с `outgoingState` хоста. Цена: 0, переиспользование спринта 12-b.
- **`shotId = (matchId=seed, shotSeq, shooterId)`**, `lastAppliedSeq` на отправителя. Цена: 0.
- **Очередь — из `state.turnReason`/`nextPlayer`**, не по чётности (§8:244). Цена: 0.
- **Внешних библиотек нет.** Цена: только время.

## Отложено (осознанно вне 02-d)

- **Контрольная сумма `Invite`** (§8:247-249) — для игры по ссылке не требуется; код повреждён не диагностируется явно. Вернуться при полировке лобби.
- **Игровой реванш в `Session`/`protocol`** — сейчас только лобби (`ui/lobby/rematch.ts`); реванш = новый seed/matchId.
- **Полный буфер неупорядоченных ударов** сверх простого случая — WebRTC-канал упорядочен, кейс редкий.
- **Кросс-платформенный квантованный хеш** — если понадобится (сейчас хеш по сырым float).
- **Рейтинг `game/<id>`** — общий долг, не эта подфаза.
